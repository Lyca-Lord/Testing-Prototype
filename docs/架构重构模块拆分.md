# 架构重构模块拆分

> 本文档汇总了围绕《猫咪十字军》（CrusaderCat）正式版代码架构重构讨论中提出的全部类（Class）清单，
> 按模块分组列出职责说明，供迁移进策划案知识库后续维护。内容来自对当前原型工程
> （`Project/CursaderCat_Prototype/Assets/Script/LYCA/`）的代码走查与架构讨论，
> 原型中对应的旧类名已在括号中注明，便于对照。

## 一、核心设计原则回顾

1. **逻辑与表现分离**：任何"看得见"的东西（位移插值、受击反馈、死亡表现、指示器开关、涟漪动画）都应该收敛到独立的表现层类中，逻辑层只负责判定规则、广播"请播放 XX 表现"的请求，并等待表现层回调完成。
2. **数据驱动优先于硬编码**：技能效果、地图数据、关卡配置都应该是可在 Inspector 里配置的 ScriptableObject + 可插拔的接口实现，而不是写死在某个"管理器"类里的 if/switch 分支。
3. **可嵌套的全体指令**：全体行动（打出一张卡让所有单位执行一次该行动）需要支持"指令批次"可以在执行过程中临时插入新的批次（如传令官技能），而不是靠一个全局唯一状态字段锁死。
4. **回合推进权威统一**：回合/阶段的切换逻辑应该集中在一个状态机里，而不是分散在卡牌列、AI 控制器、全局静态字段里各自判断。

## 二、数据层（ScriptableObject / 纯配置数据）

| 类名 | 原型中对应 | 职责说明 |
|---|---|---|
| `ChessDefinition` | `UnitInfo` | 单位的静态数值、技能列表、外观、费用等配置数据 |
| `SkillDefinition` | `Trait`（空壳）+ `TraitManager`（硬编码效果） | 技能配置资源：触发时机（`SkillTriggerType`）+ 一组可插拔效果（`ISkillEffect` 列表），新增技能通常只需配置数据，不需要写代码 |
| `ActionCardDefinition` | `CardInfo` | 行动卡配置：对应的行动类型、文案、图标，替代现在靠 `cardId` 做 switch 的硬编码方式 |
| `MapLayoutAsset` | `LevelMapInfo` 中的地形部分 | 纯地形数据（宽高、每格类型、旗帜位置），可被多关卡复用，供自定义地图编辑器导出 |
| `DeploymentAsset` | `LevelMapInfo.originEnemyInfos` | 某张地图上"谁在哪出生"的编排数据，直接引用 `ChessDefinition`，不走字符串反查资源路径 |
| `EnemyRosterAsset` | `LevelInfo.weightList`（`EnemyUnitPriorPair`） | 敌方兵种权重表，直接引用 `ChessDefinition` + 权重数值，替代字符串名字匹配 |
| `TileSkinSet` | `MapCell.oddSprite`/`evenSprite` | 地形类型到美术表现（贴图/预制体变体）的映射表，编辑器预览和运行时渲染共用同一份 |
| `LevelDefinition` | `LevelInfo` | 顶层关卡装配器：引用以上资源 + 双方 `ChessDefinition` 池、卡组 |

## 三、技能系统

| 类名 | 原型中对应 | 职责说明 |
|---|---|---|
| `SkillDefinition` | （见上表） | 技能配置资源本体 |
| `SkillTriggerType`（枚举） | 无（原来靠手动 `AddListener` 决定触发时机） | 技能的触发时机枚举（如近战结算后、远程结算后、回合开始等），新增触发时机只需加枚举项 + 在 `SkillSystem` 里补一行事件订阅 |
| `SkillContext` | 无 | 技能触发时传递给各效果的上下文数据（施法者、关联指令、技能定义自身） |
| `ISkillEffect`（接口） | 无（效果逻辑硬编码在 `TraitManager` 的私有方法里） | 单个技能效果的统一接口，新增效果类型只需新建实现类 |
| `ShieldEffect` | `TraitManager.TraitMachine_Trait_FightwithShield` | 护盾效果：为施法者增加指定数量护盾，数值可配置 |
| `BonusMoveEffect` | `TraitManager.TraitMachine_Trait_CavalryCharge` | 追加移动效果：插入一条额外的战术调整指令，距离可配置 |
| `KnockbackEffect` | `TraitManager.TraitMachine_Trait_Pull` | 击退效果：将目标沿方向推开指定距离，可附加伤害 |
| `SkillSystem` | `TraitManager` | 统一订阅 `Central` 领域事件，按触发时机分发给相关单位的技能定义执行；也是技能向 `ActionBatchStack` 压入嵌套批次（如传令官技能）的唯一入口 |

## 四、可嵌套全体指令引擎（替代 `CardEffect` 中四份重复流程）

| 类名 | 原型中对应 | 职责说明 |
|---|---|---|
| `ActionBatchSpec` | 无（流程硬编码在 `CardEffect` 的 `XxxEnter` 方法里） | 纯数据，描述"这一批全体指令要做什么"：行动类型、候选单位过滤条件、数值覆盖、发起来源、是否允许提前结束 |
| `ActionBatchRunner` | `CardEffect` 的 `XxxEnter/XxxSelectUnit/XxxActionEnd/XxxCheckEnd/XxxCommandEnd` 系列方法 | 每次使用都新建实例（非单例共享字段），独立维护本批次的候选单位与事件订阅，避免多批次互相抢监听 |
| `ActionBatchStack` | `CardEffect.isLock`（单一锁字段） | 全局唯一的"批次栈"，支持 `Push` 压入新批次并挂起栈顶批次、批次完成后自动出栈恢复下层批次，是"嵌套"能力的核心实现 |
| `ActionResolverRegistry` | `CardController.ShowCardSelectIndicator` 中的 switch-case | 维护"行动类型 → 候选过滤条件/合法性校验"的映射表，新增行动类型只需注册一条 |

## 五、回合与阶段管理

| 类名 | 原型中对应 | 职责说明 |
|---|---|---|
| `TurnManager` | `Central.currentBattlePhrase`（形同虚设）+ `CardColumn.NextTurn` 中混杂的回合副作用 | 唯一权威的回合/阶段状态机（部署→战术→战斗→歼灭循环），对外广播"回合开始/结束"等事件，各模块各自订阅并只做自己职责内的事 |
| `DeploymentDirector` | `DeployPhaseManager` | 作为 `TurnManager` 的"部署阶段"驱动器之一，纳入统一回合循环而非独立于外的一次性脚本 |
| `AIDirector` | `AIController` / `AIController_Two`（两份并存） | 由 `TurnManager` 在进入敌方回合阶段时统一调用的 AI 决策入口，建议评审后合并为一套 |

## 六、单位（Chess，原 `Units`）

拆分为三层，避免逻辑、状态机、表现揉在同一个类里：

| 类名 | 原型中对应 | 职责说明 |
|---|---|---|
| `Chess` | `Units` | 逻辑门面：身份归属、锁定状态、位置、指令接收分发、技能查询、数值结算转发；不直接操作任何 `SpriteRenderer` |
| `ChessStats` | `UnitElement`（数值部分） | 承载具体数值（生命、护盾、攻击、移速、战术调整力）与结算规则 |
| `ChessCommand` | `UnitCommand` | 指令数据：执行者、指令类型、目标坐标、是否可取消/跳过 |
| `ChessActionKind`（枚举） | `ActionType` | 指令类型枚举 |
| `ChessActionState`（抽象基类） | `UnitState` | 指令状态基类，只负责推进"执行到哪一步"，不直接操作 `Transform` |
| `ChessStateMachine` | `StateMachine` | 在不同 `ChessActionState` 间切换 |
| `ChessIdleState` / `ChessMoveState` / `ChessMeleeState` / `ChessRangedState` / `ChessTacticState` / `ChessReinforceState` / `ChessWaitForXxxState` | `IdleState` / `MoveState` / `MeleeState` / `RangedState` / `TacticState` / `ReinforceState` / `WaitForMoveState` 等 | 各类具体指令状态，调用 `IChessView` 接口完成表现，不自己写插值/等待 |
| `IChessView`（接口） | 无 | 表现层对外契约：播放移动/击退/受击/死亡表现，指示器与排序层级开关 |
| `ChessView` | `Units` 中的 `square`/`pickIndicator`/`cardSelectIndicator`/`ChangeSortingOverlay`/`GetHit` 等视觉相关代码 | 表现层默认实现：位移插值、受击闪白、死亡淡出、指示器开关、排序层级同步，只管"演"，不做规则判断 |
| `ActionSequencer` | `UnitCommandManager` | 单个 Chess 的指令执行驱动（出栈→交给状态机→等待完成→继续下一条），批量选人逻辑移交 `ActionBatchRunner` |
| `ChessRoster` | `UnitManager` | Chess 实例的生成、注册、生命周期管理（增援、死亡移除） |

## 七、棋盘与格子（BattleTile，原 `MapCell`）

| 类名 | 原型中对应 | 职责说明 |
|---|---|---|
| `BoardManager` | `MapManager` | 棋盘数据与查询：格子检索、寻路、距离计算、"哪些格子应当可交互"的纯计算，不直接管动画/渲染 |
| `BattleTile` | `MapCell` | 代表一个格子：坐标、地形类型、占用状态查询/变更、交互开关（带语义标签）、路径预览设置、点击事件广播；不管寻路算法、不管"为什么此刻要高亮" |
| `GridCoordinate`（结构体） | 直接复用 `Vector2` 当索引 | 专门的整数坐标结构体，替代用浮点 `Vector2` 当网格索引，避免潜在的浮点比较问题 |

## 八、动画与表现层

| 类名 | 原型中对应 | 职责说明 |
|---|---|---|
| `TileHighlightPresenter` | `MapManager.EnableCellByRange`/`HighLightMovePath` 中直接调用 `EnableClick()` 的部分 | 接收"可交互格子集合 + 触发源坐标"，按距离错开延迟，播放涟漪扩散式逐格显现动画 |
| `AnimationGate` / `IPresentationHandle` | 各处硬编码的 `yield return new WaitForSeconds(固定数字)` | 统一的"等待某个表现动画播完"抽象，供 `TurnManager`/`ActionBatchRunner`/`ActionSequencer` 使用，替代猜时长的写法 |
| `ChessView` | （见上表，单位表现） | 同时属于本模块 |
| `CardUI` / `TurnBanner` / `CommandToast` | `CardUI` / `TurnText` / `CommandText` | UI 展示层，订阅领域事件做纯展示，不反向持有领域逻辑 |

## 九、自定义地图编辑器工具链（编辑器态）

| 类名 | 原型中对应 | 职责说明 |
|---|---|---|
| `MapEditorWindow` | 无（现仅有 `LevelMapReader` 的右键菜单一次性导入） | 自定义地图编辑器主窗口，用于绘制地形、摆放出生点、挂载旗帜 |
| `MapAuthoringDocument` | `LevelMapInfo.LoadFromJson` 读取的 JSON 中间结构 | 编辑器内部的富编辑数据（可含分组、注释等编辑态专属信息），与运行时资产分离 |
| `MapAssetExporter` | `LevelMapReader.LoadMapsFromJsons` | 将 `MapAuthoringDocument` 转换并写出为 `MapLayoutAsset`/`DeploymentAsset`，转换时跑统一校验 |
| `LevelAssetValidator` | 无（现状缺少校验，仅运行时才暴露配置错误） | 编辑器保存/导出与运行时加载共用的同一套校验规则（出生点越界、引用缺失等） |

## 十、已知需要重点替换的原型技术债（对照说明）

1. **`LevelMapInfo.LoadFromJson` 依赖 `#if UNITY_EDITOR` 包裹的 `AssetDatabase.LoadAssetAtPath` 按字符串单位名反查资源**：构建后无法运行时加载 JSON，是关卡配置重构必须解决的硬伤，由 `MapAssetExporter` + 强类型引用的 `DeploymentAsset` 替代。
2. **`UnitElement.CheckTraits(string)` 按 `Trait.name`（资源文件名）做字符串比较**：改名即失效，由 `SkillDefinition.skillId`（稳定标识符，非文件名）替代。
3. **`CardEffect` 中 Move/Melee/Ranged/Tactic 四份几乎相同的流程**：由 `ActionBatchRunner` + `ActionResolverRegistry` 统一收敛，新增行动类型不再需要复制整套流程。
4. **`AIController`/`AIController_Two` 两份并存**：建议评审后合并为统一的 `AIDirector`，由 `TurnManager` 统一调度。
5. **`Central.currentBattlePhrase`（`GamePhase` 枚举）声明后从未被真正使用**：由 `TurnManager` 接管，让阶段机制真正生效。

## 十一、建议落地顺序

1. `BoardManager`/`BattleTile` 坐标结构体与接口收敛 + `TileSkinSet`（风险最低，为地图编辑器打基础）。
2. `ActionBatchSpec`/`ActionBatchRunner`/`ActionBatchStack`（先等价重写现有四种行动，验证可嵌套性）。
3. `TurnManager`（收拢回合推进权威，为技能系统的触发锚点打基础）。
4. `SkillSystem`/`SkillDefinition`/`ISkillEffect`（实现传令官技能作为首个嵌套批次示范用例）。
5. `TileHighlightPresenter` 的涟漪动画与 `AnimationGate` 统一等待机制。
6. 自定义地图编辑器（`MapEditorWindow`/`MapAuthoringDocument`/`MapAssetExporter`/`LevelAssetValidator`）可与前述步骤并行开发，只需先定稿 `MapLayoutAsset`/`DeploymentAsset`/`TileSkinSet` 的数据结构。

7. `Chess`/`ChessView`/`ChessActionState` 三层拆分可在 2～3 之间穿插进行，建议先搬运纯表现相关字段与方法到 `ChessView`，再逐步把 `MoveState` 等状态类中手写的插值/等待改为调用 `IChessView` 接口并等待回调。
